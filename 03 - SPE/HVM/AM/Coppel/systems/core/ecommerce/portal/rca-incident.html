Análisis técnico

Causa raíz — cinco porqués

Metodología blameless. La causa raíz no es la persona, es el sistema que permitió que ocurriera.

01
¿Por qué falló el carrito?
Síntoma visible
El pool de conexiones de SFCC Basket API alcanzó su límite de 50 conexiones simultáneas. Todos los nuevos requests recibieron HTTP 503.
02
¿Por qué se saturó el pool?
Causa inmediata
El tráfico de addToCart alcanzó 68 req/seg durante la venta nocturna, superando en 36% el baseline histórico. Es el tercer evento de alta demanda nocturna en 90 días con el mismo comportamiento. El límite del pool nunca se revisó antes del evento.
03
¿Por qué no hubo retry automático?
Gap en el spec
El AC-5 del spec define un retry con backoff de 500ms antes de escalar el error al usuario. Este criterio no estaba implementado en el subgraph carrito en producción.
04
¿Por qué no activó el circuit breaker?
Gap en el spec
El AC-6 define un circuit breaker que se abre tras 5 errores consecutivos y activa un fallback de cola. Tampoco estaba configurado en producción.
05
¿Por qué los ACs no llegaron a producción?
Causa raíz profunda
No existe un gate automático en el pipeline CI/CD que valide la equivalencia entre el spec (ACs documentados) y el comportamiento en producción. Los ACs se definen en el spec pero no se verifican en el pipeline antes del deploy. Esta es la causa raíz sistémica que permitió que el gap existiera durante semanas sin ser detectado.

subgraphs/carrito/src/resolvers/cart.resolver.ts ✓ remediado — implementa AC-5 y AC-6 
import { SFCCBasketClient } from '../clients/sfcc-basket.client';
import { CircuitBreaker } from '../resilience/circuit-breaker';
import { AddToCartInput, AddToCartResult, UserError } from '../types';
import { CARRITO_CB_CONFIG } from '../config/circuit-breaker.config';

/** Espera N milisegundos (para backoff) */
const sleep = (ms: number) => new Promise(r => setTimeout(r, ms));

export class CartResolver {
  private cb = new CircuitBreaker(CARRITO_CB_CONFIG);

  constructor(private sfcc: SFCCBasketClient) {}

  async addToCart(input: AddToCartInput): Promise<AddToCartResult> {
    // AC-6: circuit breaker — se abre tras 5 errores consecutivos
    return this.cb.execute(async () => {
      let lastError: Error | undefined;

      // AC-5: 1 retry con backoff exponencial de 500ms
      for (let attempt = 0; attempt <= 1; attempt++) {
        try {
          const response = await this.sfcc.post(
            `/baskets/${input.basketId}/items`,
            { productId: input.productId, quantity: input.quantity },
            { timeout: 3000 }  // AC-5: timeout estricto de 3 000ms
          );
          return this.mapResponse(response);
        } catch (err: any) {
          if (err.status === 503 && attempt === 0) {
            lastError = err;
            await sleep(500);  // backoff antes del retry
            continue;
          }
          throw this.mapError(err);
        }
      }
      throw this.mapError(lastError!);
    });
  }

  private mapError(err: any): UserError {
    if (err.status === 503) return {
      code: 'BASKET_POOL_EXHAUSTED', message: 'error.cart.pool_exhausted', retryable: true
    };
    return { code: 'UNKNOWN', message: 'error.generic', retryable: false };
  }
}

import { CircuitBreakerConfig } from '../resilience/circuit-breaker';
import { UserError } from '../types';

export const CARRITO_CB_CONFIG: CircuitBreakerConfig<UserError> = {
  failureThreshold:  5,      // 5 errores consecutivos → circuit abierto
  timeout:           3000,   // 3s timeout por request (AC-5)
  resetTimeout:      30000,  // 30s antes de intentar half-open
  onOpen: () => {
    // Emitir métrica a Datadog cuando el circuit se abre
    datadogRUM.addAction('circuit_breaker.open', { subgraph: 'carrito' });
  },
  fallback: async (): Promise<UserError> => ({
    code: 'BASKET_POOL_EXHAUSTED',
    message: 'error.cart.pool_exhausted',
    retryable: true
  })
};

// Tests de validación para AC-5 y AC-6 — ejecutar en QA antes de promover a PROD

describe('CartResolver — resilience (AC-5, AC-6)', () => {

  it('AC-5: reintenta 1 vez con 500ms backoff si SFCC responde 503', async () => {
    const sfcc = mockSFCC([{ status: 503 }, { status: 200, data: cartOK }]);
    const start = Date.now();
    const result = await new CartResolver(sfcc).addToCart(sampleInput);
    const elapsed = Date.now() - start;

    expect(result.success).toBe(true);
    expect(sfcc.post).toHaveBeenCalledTimes(2); // 2 intentos
    expect(elapsed).toBeGreaterThanOrEqual(500); // backoff aplicado
  });

  it('AC-5: retorna BASKET_POOL_EXHAUSTED si ambos intentos fallan', async () => {
    const sfcc = mockSFCC([{ status: 503 }, { status: 503 }]);
    const result = await new CartResolver(sfcc).addToCart(sampleInput);

    expect(result.success).toBe(false);
    expect(result.userError?.code).toBe('BASKET_POOL_EXHAUSTED');
    expect(result.userError?.retryable).toBe(true);
  });

  it('AC-6: circuit breaker se abre tras 5 errores consecutivos', async () => {
    const sfcc = mockSFCC(Array(12).fill({ status: 503 }));
    const resolver = new CartResolver(sfcc);

    // 5 errores → circuit abierto
    for (let i = 0; i < 5; i++) await resolver.addToCart(sampleInput);

    // El 6to request usa el fallback sin llamar a SFCC
    const callsBefore = sfcc.post.mock.calls.length;
    await resolver.addToCart(sampleInput);
    expect(sfcc.post.mock.calls.length).toBe(callsBefore); // no llamó a SFCC
  });

  it('AC-5: timeout de 3 000ms se aplica en cada intento', async () => {
    const sfcc = mockSFCC([{ delay: 4000, status: 200 }]);
    const result = await new CartResolver(sfcc).addToCart(sampleInput);
    expect(result.success).toBe(false); // timeout → error
  });
});

Lecciones aprendidas

LECCIÓN 01
Los AC de resiliencia necesitan gates automáticos en el pipeline
AC-5 y AC-6 estaban documentados en el spec desde el inicio del sprint. El pipeline de deploy los promovió a producción sin verificar su implementación. Un AC que define comportamiento resiliente debe tener un test automatizado que falle si no está presente — no basta con que esté escrito.
LECCIÓN 02
Los límites de recursos no se revisan antes de eventos de alto tráfico predecibles
El pool de 50 conexiones saturó en tres ventas nocturnas consecutivas en 90 días. La venta nocturna es un evento predecible y recurrente — no fue una sorpresa. No existe un proceso que revise límites de recursos antes de cada evento de alto tráfico. El patrón era detectable; el proceso de prevención no existía.
LECCIÓN 03
Los monitores de Datadog detectaban síntomas, no causas
La alerta se disparó cuando el error rate ya era del 98% — el sistema estaba completamente caído. Datadog tenía datos de utilización del pool pero no había un monitor al 75% que generara señal preventiva. Los datos existían; faltó la regla que los convirtiera en alerta accionable.
