WFL_SPLUNK · Orquestador de integración Splunk — arranque, parada y depuración de STSTOTALES (CORE-GL)

CORE-GLWFLWFL

Fuente: WFL_SPLUNK.wfl (98 LOC) · job de orquestación batch WFL · BC-XX (sin BC de negocio: arquitectura AS-IS · REEMPLAZAR ORQUESTADOR)

Convenciones: nombres traducidos (Unisys WFL→legible); [WFL_SPLUNK Lnnn] = línea física del fuente; (BR: RN-CORE-GL-nnnn) = regla del KB.

% = comentario en WFL. Líneas con número de secuencia MCP: el campo numérico de 8 dígitos al final de cada línea es el número de secuencia del editor MCP — no es código.

1. Resumen funcional

Job WFL que actúa como punto de control operativo de la integración del CORE-GL con la plataforma de observabilidad Splunk. Su función es exclusivamente orquestadora: no genera ni transmite datos directamente a Splunk, sino que inicia, detiene o limpia el entorno de ejecución del programa P810/STSTOTALES (CORE-GL/OBJECT/P810/STSTOTALES/25MTP006), que es quien produce los totales estadísticos enviados a Splunk.

El job expone tres modos de operación seleccionados por PARAM1 (INICIA / TERMINA / DEPURA) con un sub-selector PARAM2 (P810 / ALL) para los dos primeros: al INICIAr, señaliza graciosamente la instancia activa de P810 (si la hay) vía el utilitario P804/TCMD del sistema S288 corriendo en la mix-station SPLUNK, y luego lanza una nueva instancia; al TERMINAr, envía solo la señal de parada; al DEPURAr, elimina los archivos de trabajo de STSTOTALES (CTL, LOG, CON) de las familias CMEMP y LOGS.

La dependencia principal es P810/STSTOTALES, que sí existe en el corpus CORE-GL. Las utilidades de comunicación con la mix-station Splunk (P804/TCMD y P805/REMF) pertenecen al sistema S288 y no están en el corpus CORE-GL — constituyen una dependencia externa inter-sistema (ver §5, §4.1).

« divergencia KB: RN-CORE-GL-1163 » — La ficha KB describe el WFL como un job que "dispara el flujo de generación y transmisión de reportes/totales [...] hacia Splunk" con fórmula lineal de un único parámetro. El código real: (a) tiene dos parámetros (PARAM1 obligatorio + PARAM2 opcional); (b) no transmite directamente a Splunk — es un dispatcher de ciclo de vida con tres modos; (c) la "transmisión" es mediada por P804/P805 de S288. Se documenta el código; la ficha refleja la intención de alto nivel pero no la mecánica real.

2.7 TASKSTRING — parámetro de ejecución de P810

En los modos INICIA/P810 [L50] e INICIA/ALL [L58], tras el RUN #PASO810[T1] se asigna:

TASKSTRING = "COMPANY=LEGACYCORE;USER=CORE-GL;PACK=CMEMP;BASE_DIR=CORE-GL_FILE;"

Esta asignación ocurre después del RUN — es inyección tardía de parámetros sobre la tarea ya lanzada (mecanismo MCP de comunicación con tarea activa).

⚠ [HARDCODE-SOSPECHOSO] Los valores COMPANY=LEGACYCORE, USER=CORE-GL, PACK=CMEMP, BASE_DIR=CORE-GL_FILE están literales. No hay parámetro ni variable que los externalice. Son datos de identidad del entorno de producción LegacyCore.

3. Mapa de control (DAG de ejecución)

El job es un dispatcher de tres modos seleccionado por PARAM1. Dentro de los modos INICIA y TERMINA, hay un segundo selector por PARAM2. No hay flujo secuencial implícito entre modos — cada invocación del job ejecuta exactamente una rama.

WFL_SPLUNK (PARAM1, PARAM2 = "NADA")
│
├── [ON RESTART] → GO INICIO           [L32]      (manejador de reinicio)
│
└── INICIO:                            [L33-L37]  (inicialización de variables)
    │
    CASE PARAM1:
    │
    ├── "INICIA"                        [L40]
    │    CASE PARAM2:
    │    ├── "P810"                     [L43-L52]
    │    │    ├── [ON TASKFAULT] → GO REINP810    [L45]
    │    │    ├── TASKCOMM(P810, "HI 4")           [L46]   ← señaliza instancia activa (si existe)
    │    │    ├── REINP810:                        [L47]
    │    │    ├── INITIALIZE(T1)                   [L48]
    │    │    ├── RUN P810/STSTOTALES [T1]         [L49]
    │    │    ├── TASKSTRING = "..."               [L50]   ← inyección tardía de parámetros
    │    │    └── WAIT(T1 IS COMPLETED)            [L51]   ← SÍNCRONO
    │    │
    │    ├── "ALL"                      [L53-L59]
    │    │    ├── TASKCOMM(P810, "HI 4")           [L55]
    │    │    ├── INITIALIZE(T1)                   [L56]
    │    │    ├── RUN P810/STSTOTALES [T1]         [L57]
    │    │    └── TASKSTRING = "..."               [L58]   ← sin WAIT → ASÍNCRONO
    │    │
    │    └── ELSE: DISPLAY error PARAM2            [L60-L64]
    │
    ├── "TERMINA"                       [L66]
    │    CASE PARAM2:
    │    ├── "P810"                     [L69-L72]
    │    │    └── TASKCOMM(P810, "HI 4")           [L71]
    │    │
    │    ├── "ALL"                      [L73-L76]
    │    │    └── TASKCOMM(P810, "HI 4")           [L75]   ⚠ idéntico a TERMINA/P810
    │    │
    │    └── ELSE: DISPLAY error PARAM2            [L77-L81]

Conteo de nodos DAG (pasos lógicos distintos): 10 nodos (ver gate §5).

4. Lógica por sección

4.1 Subroutine TASKCOMM — Envío de comando a programa activo en Splunk

« [WFL_SPLUNK L9-L19] »

SUBRUTINA Enviar_Comando_Splunk(programa_titulo, comando_mcp):
    // Parámetros: PROG=título del programa destino; CMD=cadena de comando MCP
    DECLARAR tarea_local  // TT: descriptor de tarea local
    DECLARAR usuario_actual  // MIUSER: STRING

    usuario_actual := OBTENER_USERCODE_ACTUAL()
    // MYSELF(USERCODE) → usercode del job en ejecución  [WFL_SPLUNK L15]

    EJECUTAR (S288)S288/OBJECT/P804/TCMD/01MTP002
        EN mix-station SPLUNK
        CON ARGUMENTOS (usuario_actual, programa_titulo, comando_mcp)
        EN TAREA tarea_local
    // RUN ON SPLUNK: lanza P804/TCMD en la mix-station de nombre SPLUNK  [WFL_SPLUNK L16-L17]
    // P804/TCMD pertenece a S288 — NO está en corpus CORE-GL

    ESPERAR 5 segundos
    // WAIT(5) — espera fija de 5 segundos para que el comando surta efecto  [WFL_SPLUNK L18]
    // ⚠ Espera no adaptativa: si P810 tarda más de 5 s en responder al "HI 4", el job continúa
FIN SUBRUTINA

⚠ Nota de migración: La subrutina usa P804/TCMD de S288, un utilitario MCP propietario que encapsula el envío de mensajes HI (Halt/Interrupt) a tareas activas en la mix-station SPLUNK. En el entorno destino, este mecanismo debe sustituirse por la API de gestión del proceso equivalente (señal SIGTERM, llamada a API de scheduler, etc.).

4.4 Modo INICIA / Sub-modo P810 — Arranque controlado y síncrono de P810

« [WFL_SPLUNK L43-L52] »
« BR: RN-CORE-GL-1163 (parcial) »

SI PARAM1 = "INICIA" Y PARAM2 = "P810":

    CUANDO EVENTO=ERROR_TAREA → IR_A Reiniciar_P810
    // ON TASKFAULT,GO REINP810: si el TASKCOMM falla (la instancia de P810 no está activa),
    // salta la señalización y va directo a lanzar la nueva instancia  [WFL_SPLUNK L45]
    // Patrón: arranque defensivo — falla silenciosa de pre-terminación

    LLAMAR Enviar_Comando_Splunk(
        programa_titulo = DERIVAR_PREFIJO(ruta_p810),   // TAKE(PASO810, LENGTH-9) elimina "/25MTP006" del título
        comando_mcp     = "HI 4"
    )
    // Señaliza graciosamente la instancia activa de P810 con HI 4 (Halt/Interrupt nivel 4)
    // "HI 4" = MCP Mix command: instruye al programa detenerse al completar el ciclo actual  [WFL_SPLUNK L46]
    // Si no hay instancia activa → TASKFAULT → salta a Reiniciar_P810

    Reiniciar_P810:                                      // [WFL_SPLUNK L47]
    INICIALIZAR descriptor_tarea_global                  // INITIALIZE(T1) [WFL_SPLUNK L48]

    LANZAR CORE-GL/OBJECT/P810/STSTOTALES/25MTP006         // RUN #PASO810[T1] [WFL_SPLUNK L49]
        EN TAREA descriptor_tarea_global

    descriptor_tarea_global.TASKSTRING :=
        "COMPANY=LEGACYCORE;USER=CORE-GL;PACK=CMEMP;BASE_DIR=CORE-GL_FILE;"
    // Inyección tardía de parámetros sobre la tarea ya lanzada  [WFL_SPLUNK L50]
    // ⚠ [HARDCODE-SOSPECHOSO] Valores de identidad de entorno LegacyCore cableados

    ESPERAR A QUE descriptor_tarea_global COMPLETE
    // WAIT(T1 IS COMPLETED) — ejecución SÍNCRONA: el job queda bloqueado hasta que P810 termine  [WFL_SPLUNK L51]

FIN SI

⚠ Asimetría INICIA/P810 vs INICIA/ALL: Solo P810 espera la finalización (WAIT). El modo ALL es asíncrono (ver §4.5). Esto sugiere que P810 tiene un tiempo de ejecución conocido y controlado, mientras ALL dispara el proceso y lo deja correr en background.
