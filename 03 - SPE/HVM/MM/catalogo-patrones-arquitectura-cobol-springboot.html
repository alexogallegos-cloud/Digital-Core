Estrategias de Migración — Las 7R

Framework de decisión para clasificar cada aplicación del portafolio mainframe antes de diseñar su plan de migración.

🔊
Rehost (Lift & Shift)
Ejecutar el COBOL compilado en x86 sin cambios de código. Emulador z/OS (Micro Focus, Blu Age). Sin refactorización de datos. Deuda técnica persiste.
Riesgo de performance
⚙
Replatform
COBOL compila en x86; BD migra a RDS/Aurora; JCL reemplazado por Airflow. Sin reescritura de lógica de negocio. SORT sigue en JVM — performance a validar.
Validar volumen real
🔧
Refactor
Reimplementar la intención de negocio en Java/Spring Boot con patrones correctos. N+1 corregido. Batch chunk-oriented. Recomendado para batch crítico.
Recomendado para batch
🏛
Rearchitect
Descomponer en microservicios por Bounded Context. DDD completo. Event-driven. Para sistemas con alto valor diferenciador y deuda técnica severa.
Alta inversión / alto valor
🔄
Replace
Sustituir por SaaS/COTS. Evaluar cuando el sistema implementa funcionalidad genérica (CRM, HR, contabilidad general). Decisión de negocio, no solo técnica.
Análisis TCO obligatorio
🔒
Retain / Retire
Retain: integraciones excesivas o regulación que impide mover. Retire: dead code confirmado — retirar sin migrar. Verificar TWS antes de Retire.
Validar scheduler TWS

¿El sistema tiene valor de negocio activo?
  NO → RETIRE (verificar scheduler TWS antes de eliminar)
  SI → ¿Existe producto COTS/SaaS que cubra el 80%+?
        SI → REPLACE (análisis TCO + roadmap de datos)

02

Patrones Maestros de Transición

Strangler Fig

El API Gateway intercepta todo el tráfico desde el día 1. Los bounded contexts se migran wave por wave. El mainframe sigue operativo hasta que cada BC tiene paridad validada.

 5 Fases de Strangler Fig en Banca

Fase 1 — Foundation (Semana 0)
API Gateway instalado. Mainframe recibe 100% del tráfico. Sin cambios funcionales. Solo observabilidad en el gateway. Sin esto, el Strangler Fig no funciona.
Fase 2 — Shadow Mode (Semanas 1–8 por BC)
Primer BC desplegado en Java. ShadowModeFilter duplica requests de forma asíncrona al nuevo sistema. Mainframe es source of truth. Comparador acumula divergencias sin afectar usuarios.
Fase 3 — Parallel Run (Semanas 8–N)
Ambos sistemas procesan. Reconciliación diaria automática. Cutover solo si divergencia < 0.01% por 30 días consecutivos.
Fase 4 — Cutover (Fin de semana validado)
API Gateway redirige el BC al microservicio nuevo. Rollback en < 2 minutos (solo config, sin deploy). Smoke tests automáticos: 50 transacciones críticas post-cutover.
Fase 5 — Decommission (Tras 1 ciclo de negocio completo)
100% tráfico en nuevo sistema. Archivar logs COBOL según CNBV (mín. 5 años). Liberar licencias mainframe al final, no al inicio.
Anti-Corruption Layer (ACL)

Capa obligatoria en cada punto de integración COBOL⇔Java. Traduce COMP-3, PIC X, COMMAREA, fechas COBOL y EBCDIC al modelo limpio del bounded context destino.

ACL — Conversión COMP-3 (PIC S9(11)V99)
public static BigDecimal unpackComp3(
    byte[] packed, int decimalPlaces) {
  StringBuilder sb = new StringBuilder();
  for (int i = 0; i < packed.length-1; i++) {
    sb.append((packed[i] >> 4) & 0x0F);
    sb.append(packed[i] & 0x0F);
  }
  byte last = packed[packed.length-1];
  sb.append((last >> 4) & 0x0F);
  char sign = ((last & 0x0F)==0x0D) ? '-':'+';
  BigDecimal v = new BigDecimal(sb.toString())
      .movePointLeft(decimalPlaces);
  return sign == '-' ? v.negate() : v;
}
ACL — Conversión de tipos COBOL
// PIC 9(8) YYYYMMDD → LocalDate
public static LocalDate parseCobolDate(
    String d) {
  return LocalDate.parse(d,
    DateTimeFormatter.ofPattern("yyyyMMdd"));
}

// PIC 9(6) YYMMDD (Julian) → LocalDate
public static LocalDate parseCobolDateYY(
    String d) {
  return LocalDate.parse(d,
    DateTimeFormatter.ofPattern("yyMMdd")
      .withResolverStyle(ResolverStyle.SMART));
}

// EBCDIC bytes → UTF-8 String
public static String ebcdicToString(byte[] b) {
  return new String(b, Charset.forName("IBM037"));
}

// PIC X(1) flag (Y/N, 1/0) → boolean
public static boolean cobolFlagToBoolean(
    String flag) {
  return "Y".equalsIgnoreCase(flag)
      || "1".equals(flag.trim());
}
Regla absoluta: La ACL devuelve SIEMPRE el modelo limpio del bounded context destino. El modelo COBOL (PIC X, COMP-3, COMMAREA) NUNCA cruza la frontera de la ACL hacia el nuevo sistema.
Branch by Abstraction

Permite migrar módulos sin bifurcar el repositorio. Un feature flag selecciona en runtime si se usa el adaptador COBOL o la implementación Java nueva.

// Abstracción del servicio de crédito
public interface CreditScoringService {
    CreditScore evaluate(String customerId, BigDecimal amount);
}

// Adaptador COBOL (via CTG gateway al mainframe)
@Service
@ConditionalOnProperty("feature.credit-scoring.use-cobol", havingValue="true")
public class CobolCreditScoringAdapter implements CreditScoringService {
    public CreditScore evaluate(String customerId, BigDecimal amount) {
        byte[] response = ctgGateway.execute("CRSCORE", buildCommarea(customerId, amount));
        return acl.mapToScore(response);  // ACL obligatoria: nunca exponer tipos COBOL
    }
}

// Implementación Java nueva (ML-based scoring)
@Service
@ConditionalOnProperty("feature.credit-scoring.use-cobol", havingValue="false",
    matchIfMissing=true)
public class JavaCreditScoringService implements CreditScoringService {
    public CreditScore evaluate(String customerId, BigDecimal amount) {
        CustomerProfile profile = customerRepo.findById(customerId).orElseThrow();
        return scoringEngine.evaluate(profile, amount);
    }
}
Shadow Mode

El ShadowModeFilter duplica cada request de forma asíncrona al nuevo sistema. El mainframe responde al usuario. Las divergencias se acumulan sin impacto en producción.

@Component
public class ShadowModeFilter extends OncePerRequestFilter {
    private final NewPaymentService newService;
    private final ShadowComparator comparator;
    private final Executor shadowExecutor =
        Executors.newVirtualThreadPerTaskExecutor(); // Java 21+

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
            FilterChain chain) throws ServletException, IOException {
        // Envolver request para permitir relecura del body
        ContentCachingRequestWrapper wrappedReq = new ContentCachingRequestWrapper(req);

        // 1. Mainframe responde (path normal, no bloqueado)
        chain.doFilter(wrappedReq, res);

        // 2. Shadow async al nuevo sistema - NUNCA afecta latencia del usuario
        CompletableFuture.runAsync(() -> {
            try {
                PaymentRequest shadowReq = parseRequest(wrappedReq);
                PaymentResult shadowRes  = newService.process(shadowReq);
                comparator.compare(getMainframeResult(res), shadowRes);
                // Si divergencia: log + alerting, no exception
            } catch (Exception e) {
                log.warn("Shadow failure (silenced): {}", e.getMessage());
            }
        }, shadowExecutor);
    }
}

DDD desde COBOL — Bounded Contexts

Los copybooks COBOL son el punto de partida. Cada copybook compartido entre múltiples programas es candidato a BC. Los TRANSIDs de CICS agrupan por dominio funcional. Las tablas DB2 deben tener un solo BC dueño.

Apertura, cierre, estado de cuentas. Saldos contables. El BC más crítico: migrar al final. Parallel run mínimo: 1 ciclo mensual completo.

Capa Batch — COBOL a Spring Batch
Anti-patrón confirmado en banca Tier-1: Traducción literal COBOL→Java convierte cada READ VSAM en un round-trip JDBC de 1–5ms. 120M registros × 3ms promedio = 100 horas de I/O. La ventana batch EOD es de 6 horas — el sistema no termina nunca.
❌ Anti-patrón — Traducción literal COBOL
// Falla con 120M operaciones:
for (String accountId : millionIds) {
  // SELECT × N (N+1 problem)
  Account acc = repo.findById(accountId)
      .orElseThrow();
  BigDecimal interest = calc(acc);
  acc.setBalance(acc.getBalance().add(interest));
  repo.save(acc); // UPDATE × N
}
✔ Patrón correcto — Spring Batch Chunk
@Bean
public Step interestCalcStep(
    ItemReader<Account> reader,
    ItemProcessor<Account, Account> proc,
    ItemWriter<Account> writer) {
  return stepBuilderFactory
    .get("interestCalcStep")
    .<Account, Account>chunk(1000)
    .reader(reader)   // JdbcPagingItemReader
    .processor(proc)
    .writer(writer)   // JdbcBatchItemWriter
    .faultTolerant().retryLimit(3)
    .retry(DeadlockLoserDataAccessException.class)
    .build();
}
// JdbcPagingItemReader: equiv. READ VSAM secuencial en páginas de 1000
@Bean @StepScope
public JdbcPagingItemReader<Account> accountReader(DataSource ds) {
    return new JdbcPagingItemReaderBuilder<Account>()
        .name("accountReader").dataSource(ds)
        .selectClause("SELECT account_id, balance, product_type, rate")
        .fromClause("FROM accounts")
        .whereClause("WHERE status = 'ACTIVE'")
        .sortKeys(Map.of("account_id", Order.ASCENDING))
        .pageSize(1000)          // 1000 registros/página — NUNCA cargar todo en heap
        .rowMapper(new AccountRowMapper()).build();
}

// JdbcBatchItemWriter: 1000 UPDATEs en 1 executeBatch — equiv. REWRITE VSAM masivo
@Bean
public JdbcBatchItemWriter<Account> accountWriter(DataSource ds) {
    return new JdbcBatchItemWriterBuilder<Account>()
        .dataSource(ds)
        .sql("UPDATE accounts SET balance=:balance, updated_at=now() WHERE account_id=:accountId")
        .beanMapped().build();
}

Datos — VSAM/DB2 a Cloud

VSAM KSDS → PostgreSQL
La clave primaria del KSDS se convierte en PK. Acceso secuencial = ORDER BY key ASC con índice. START/READ NEXT = WHERE key >= :start LIMIT 1000.
Migración directa con DFDL
DB2 z/OS → Aurora PostgreSQL
Diferencias críticas: DATE/TIMESTAMP precision, DECIMAL scale, ROWID no existe, SCROLLABLE CURSOR = offset pagination. Validar siempre con volumen real de producción.
Validar decimal precision
CDC con Debezium
Change Data Capture desde DB2 z/OS sin modificar código COBOL. Debezium captura el transaction log y publica a Kafka. El nuevo sistema consume en tiempo real sin downtime.
Sin downtime / sin tocar COBOL
ORM en Batch — Prohibido
JPA/Hibernate en batch genera: N+1, dirty checking overhead, first-level cache que crece hasta OOM para millones de registros. Usar JdbcTemplate o JdbcBatchItemWriter directo.
Anti-patrón crítico en batch

CDC vs Dual-Write — árbol de Decisión

¿Puedes modificar el código COBOL fuente?
  NO → CDC con Debezium (captura transaction log DB2 sin cambios en COBOL)
  SI → ¿El volumen es < 100K registros/día?
        SI → Dual-Write temporal (COBOL escribe en DB2 + llama API nueva)
        NO → CDC con Debezium + Kafka (alta throughput)
Control obligatorio post-migración de datos: Comparar SUM de todos los campos monetarios entre mainframe y destino. Un campo PIC S9(11)V99 COMP-3 mal convertido produce saldos incorrectos sin errores explícitos. Si difieren en cualquier centavo: detener y corregir antes de continuar.

Patrones de Resiliencia

Circuit Breaker
Resilience4j en cada llamada al mainframe legacy durante coexistencia. Estados: CLOSED (normal) / OPEN (falla) / HALF_OPEN (probando recuperación). Fallback a caché o error controlado.
Obligatorio en ACL
Retry con Backoff Exponencial
Máximo 3 intentos con jitter (evita thundering herd). Solo para errores transitorios (timeouts, 503). Nunca para errores de negocio (saldo insuficiente = no reintentar).
Solo errores transitorios
Idempotency Key
UUID generado por el cliente en header X-Idempotency-Key. Tabla dedup con estado PROCESSING/COMPLETED/FAILED. Obligatorio para pagos, débitos, cualquier mutación financiera.
Obligatorio en pagos
Saga Orquestada
Para transacciones que tocan 3+ microservicios (SPEI: reservar→Banxico→débito→notificar). Compensating transactions automáticas. Temporal.io recomendado sobre Step Functions.
SPEI / transferencias
CQRS
Comandos (escritura) y queries (lectura) en modelos separados. Obligatorio para BC-08 Reporting: proyección de lectura optimizada, nunca consultar tablas transaccionales directamente.
Regulatorio / Performance
Event Sourcing
Eventos inmutables como fuente de verdad. Estado = replay de eventos. Obligatorio para BC-07 General Ledger y BC-08 Reporting bajo CNBV (auditoría completa de todos los cambios).
Auditoría CNBV

ResilientMainframeGateway — Composición Resilience4j

@Service
public class ResilientMainframeGateway {

    private final CircuitBreaker cb = CircuitBreaker.ofDefaults("mainframe");
    private final Retry retry = Retry.of("mainframe", RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(500))
        .retryOnException(e -> e instanceof MainframeTimeoutException)
        .build());
    private final TimeLimiter tl = TimeLimiter.of(
        TimeLimiterConfig.custom().timeoutDuration(Duration.ofSeconds(5)).build());

    public <T> T execute(String transid, byte[] commarea, Class<T> responseType) {
        Supplier<CompletableFuture<T>> futureSupplier = () ->
            CompletableFuture.supplyAsync(() ->
                ctgGateway.executeWithAcl(transid, commarea, responseType));

        return Decorators.ofSupplier(
                TimeLimiter.decorateFutureSupplier(tl, futureSupplier))
            .withCircuitBreaker(cb)
            .withRetry(retry)
            .withFallback(MainframeUnavailableException.class,
                e -> fallbackCache.getOrThrow(transid, commarea, responseType))
            .get();
    }
}

Anti-patrones Críticos

Base empírica: Estos anti-patrones causaron fallos de performance reales en proyectos de banca Tier-1. Son predecibles y evitables cuando se conocen antes de iniciar la implementación.
#1 — Traducción Literal COBOL → Java (El Anti-patrón Madre)
El COBOL en z/OS fue optimizado para: DB2 en memoria compartida (sin latencia de red), I/O a DASD por canal físico dedicado, SORT con hardware DFSORT (fuera del address space). Traducir línea a línea convierte cada EXEC SQL SELECT en un round-trip JDBC de 1–5ms. 10M registros × 3ms = 8.3 horas de I/O puro.
Regla: Al migrar de COBOL a Java, NO migrar el algoritmo. Migrar la intención de negocio y reimplementarla con los patrones correctos del entorno destino.
#2 — N+1 Query Problem a Escala de Core Bancario
Loop COBOL con SELECT por iteración → traducido a repository.findById() en loop Java. Detectable en production query logs: SELECT * FROM accounts WHERE account_id = ? aparece 10,000,000 veces en 1 hora con el mismo plan de ejecución.
Solución: JdbcPagingItemReader con chunk(1000) + JdbcBatchItemWriter. Ver sección 04.
#3 — SORT en JVM para Datasets de Millones de Registros
list.sort() en Java para 50M registros carga todo en heap → GC storms → OOM. En z/OS el DFSORT usa hardware dedicado fuera del address space del programa. Un servidor x86 dedicado (todos los CPUs, sin competencia) corre este workload a ¼ de la velocidad del mainframe.
Regla absoluta: El SORT de datasets grandes NUNCA ocurre en la JVM. Usar: ORDER BY en SQL (motor con índices), Apache Spark, o AWS Glue.
#4 — Big Bang Rewrite
"Reescribimos todo en paralelo y hacemos cutover único en 18 meses." Falla porque: el equipo subestima el conocimiento tácito de 40 años de COBOL; la paridad funcional es imposible de verificar sin ejecutar ambos sistemas en paralelo; un cutover único elimina la posibilidad de rollback; cualquier error afecta a todos los sistemas simultáneamente.
Señales de alerta: "El mainframe tiene todo mal, mejor empezamos de cero" / "Ya tenemos los requerimientos documentados" (para un sistema de 40 años) / "El cutover va a ser un fin de semana largo."
#5 — ACL como Simple Proxy (Sin Traducción de Modelo)
La ACL devuelve CobolCuentaRecord con campos PIC X y COMP-3 sin traducir. El microservicio nuevo trabaja con tipos COBOL en Java — el mainframe "infecta" al nuevo sistema.
Regla: La ACL devuelve SIEMPRE el modelo limpio del bounded context destino. El modelo COBOL nunca cruza la frontera de la ACL.
#6 — Transacciones Distribuidas con 2PC (XA)
XA/2PC bloquea recursos en todos los nodos participantes. Si el coordinator falla, recursos bloqueados indefinidamente. La latencia se multiplica por el número de participantes. Incompatible con Kafka y la mayoría de servicios cloud managed.
Alternativa: Saga Pattern con Temporal.io + eventual consistency con compensación.
#7 — Copiar la Estructura del JCL como Microservicios
STEP010 VALCUEN → ValidateAccountsService | STEP020 CALINT → CalculateInterestService. Los STEPs del JCL son unidades de orquestación de proceso, no de dominio de negocio. El resultado es un monolito distribuido altamente acoplado por secuencia.
Correcto: Microservicios por Bounded Context de dominio. Los STEPs del JCL se mapean a tareas dentro de un Spring Batch Job, no a servicios independientes.
#8 — Omitir el Shadow Period / Parallel Run
"Ya probamos en QA con datos de prueba. El cutover es directo." Los datos de producción de 40 años tienen casos edge que ningún QA anticipa. Errores de equivalencia en sistemas financieros generan diferencias contables que tardan semanas en detectarse.
Regla: Parallel run mínimo de 1 ciclo de negocio completo. Para cierre mensual: 1 mes. Para cierre anual: 1 año. No negociable.
#9 — Migrar Sin API Gateway (Strangler Fig Incompleto)
Sin API Gateway, cada cliente (mobile, web, ATM, teller, B2B) necesita modificarse para apuntar al nuevo servicio. Con el API Gateway: CERO modificaciones en clientes durante la migración. El routing cambia en un solo punto, el rollback tarda segundos.
#10 — Ignorar COMP-3 en la Migración de Datos
El UNLOAD de VSAM puede hacer conversión parcial dejando campos COMP-3 sin desempaquetar o con escala incorrecta. Un campo PIC S9(11)V99 COMP-3 mal convertido produce saldos incorrectos sin lanzar ninguna excepción. El valor es numéricamente coherente — no hay error explícito, solo dinero incorrecto silencioso.
Control obligatorio: Comparar SUM de todos los campos monetarios entre mainframe y destino. Diferencia de 1 centavo = investigar causa raíz antes de continuar.

Lecciones de Campo — Validadas en Banca Tier-1

Fuente: Estas lecciones provienen de experiencia directa en programas de modernización de cores bancarios IBM z/OS en México y LATAM. Son observaciones de campo — no teoría — documentadas para que no se repitan en proyectos futuros. Todo dato cuantitativo fue medido en ambientes de producción o staging real con volumen real.
Principio rector: El problema casi nunca es “el lenguaje de destino es lento”. El problema es que se traduce el código pero no se re-ingeniería el modelo de ejecución. El mainframe IBM z/OS no es solo un lenguaje — es una máquina diseñada 50+ años para throughput batch: I/O secuencial de alto ancho de banda, aritmética decimal por hardware, motores SORT en assembler, y co-localización de cómputo y datos. Cuando se migra COBOL a Java con traducción literal 1:1, se pierde todo eso.
Performance — Datos Medidos
🔌
N+1 colapsa la red — 120M ops/noche
En un banco Tier-1, 120 millones de operaciones de contabilidad en un solo batch con un SELECT por registro colapsaron literalmente la red. No es metáfora — la red satura físicamente. Lo que el mainframe procesa en una ventana nocturna tardó múltiplos de esa ventana en Java.

Degradación típica: 10× a 100× sobre el tiempo de mainframe para el mismo volumen.
Causa #1 de fallo en batch
⏱
SORT x86 a ¼ de velocidad del mainframe
Servidor dedicado con todos los CPUs disponibles, sin ninguna carga concurrente, sin servicios compitiendo. Resultado: corre el SORT a un cuarto de la velocidad del mainframe.

DFSORT/SyncSort tienen 40+ años de optimización en assembler con hardware sort-assist y acceso directo a canales I/O. No hay equivalente JVM que se acerque en volumen bancario.
Solo por SORT: inaceptable EOD
⚕
COMP-3: overhead por cada cálculo
La conversión de tipos COMP-3 a BigDecimal y de regreso en cada operación acumula latencia. En 120M asientos contables, cada microsegundo de overhead por cálculo se multiplica en minutos u horas de proceso total.

El error peor: usar double para ganar velocidad — produce resultados rápidos pero rompe equivalencia contable por redondeo. Un descuadre de centavos en el ledger es hallazgo de auditoría CNBV.
BigDecimal obligatorio, sin excepción
🏢
Data locality: LPAR vs. red
DB2 en un LPAR mainframe vive en el mismo sistema físico que el batch COBOL. Acceso vía cross-memory services: microsegundos, sin red. En arquitectura distribuida, cada acceso es un round-trip de red. Combinado con N+1, esto convierte microsegundos en milisegundos × 120M operaciones.

El tier de batch debe co-localizarse con sus datos. La distancia entre proceso y datos no es detalle de despliegue — es diseño de performance.
Mismo AZ / VPC que los datos
Conversión — La Paradoja
La paradoja de la conversión determinística: Un proveedor especializado en conversión automática (“un botón, 1.5 millones de líneas convertidas”) entregó una migración funcionalmente perfecta, totalmente cuadrada: producía exactamente los mismos asientos que el mainframe. El problema: el tiempo de procesamiento hacía inviable la ventana batch nocturna. La equivalencia funcional es condición necesaria pero no suficiente. La equivalencia de performance es igualmente obligatoria.
Los agentes de IA cometen el mismo error
GitHub Copilot, Amazon Q, Claude y equivalentes tienen el mismo problema que la conversión determinística: tienden a traducción literal. El agente no distingue entre un READ secuencial de archivo y una query JDBC.

Errores específicos de IA:
• Usa el nombre de la variable COBOL como definición de la regla (en lugar de inferirla del código)
• Rellena fórmulas financieras con conocimiento genérico del dominio bancario, no con la fórmula exacta hardcodeada en el COBOL
• No ve la lógica de negocio embebida en el JCL (SORT/JOINKEYS/condiciones) — solo analiza los programas COBOL
El piloto de laptop vs. el piloto real
Piloto de proveedor europeo: 2 programas corriendo en una laptop + reporte firmado por el proveedor. Resultó: “pasaron el piloto.”

Piloto real requerido: Convertir Y probar en el ambiente DEV del banco con datos reales de producción y volumen real.

La diferencia fue “como la noche y el día”. El proveedor pasó su piloto; no tenía nada que ver con las condiciones reales de producción.

Regla: Cualquier piloto debe especificar: ¿qué ambiente?, ¿qué volumen?, ¿qué criterio de aceptación?

25 Constructos COBOL/JCL Sin Traducción Literal — Los 10 Más Críticos

ConstructoProblema de traducción literalPatrón correcto
JOINKEYS (SORT utility) El agente no replica correctamente el match entre archivos — puede perder registros, duplicar, o no respetar el orden de join. Nested-loop O(n²) vs. merge-join O(n). Merge-join sobre streams pre-ordenados. Verificar equivalencia registro a registro.
DFSORT instrucciones propietarias (COUNT, NODUP, EDIT) El agente no conoce estas instrucciones IBM — genera código que no replica el comportamiento. Catálogo de equivalencias IBM-utility → Java por cada instrucción usada en el sistema.
REDEFINES Una posición de memoria con múltiples tipos de dato según contexto. El agente crea clases separadas que rompen la semántica de memoria compartida. Union/tagged-union en Java, o BitBuffer. Validar con test de igualdad de bytes.
STRING / UNSTRING Concatenación y división con delimitadores y overflow que Java no replica con operaciones estándar. Helpers Java verificados con pruebas de comportamiento borde.
INSPECT Recuento y sustitución de caracteres en posiciones específicas — semántica distinta a String.replace(). Mapear cada uso a su equivalente exacto; no usar traducción automática.
LOW-VALUES / HIGH-VALUES Byte mínimo (0x00) y máximo (0xFF). Sin equivalente en Java String. Traducir a "" o null es incorrecto. Constantes byte[] con valor explícito 0x00/0xFF.
Ordenamientos implícitos pre-match El SORT ordena los archivos antes del match implícitamente. Si Java no replica ese orden, el join produce resultados incorrectos aunque la lógica sea correcta. Todo match en Java debe ir precedido del mismo criterio de ordenamiento del JCL.
COMP-3 / Packed Decimal No existe equivalente nativo Java. Tratar como texto plano produce valores incorrectos desde el primer registro. Capa de decodificación en ingesta con JRecord/Cobrix. Nunca tratar como texto.
Encoding EBCDIC El mainframe almacena en EBCDIC; Java trabaja en UTF-8/Unicode. Caracteres léidos sin conversión son basura. Decodificar EBCDIC a Java una vez en la capa de ingesta (Charset.forName("IBM037")).
Fechas julianas y periodos contables COBOL usa fechas julianas y períodos contables propios. Traducir a LocalDate sin conversión explícita produce fechas incorrectas. Conversión explícita + pruebas de cierres de período.
Organización — Dinámicas de Campo
🤖
La capa conversacional: Angular falló, IA resolvió
Pantallas de terminal CICS (~70% del código mainframe): un intento de modernización con Angular duró meses y fue “un desastre, no se podía mantener.” La misma capa se resolvió con agentes de IA que auto-generan la capa de presentación — en semanas, probado en ambiente DEV del banco.

La dificultad de cada capa requiere un enfoque distinto. No existe un solo patrón que resuelva online, conversacional y batch.
IA para conversacional
⚖
El 100% automatizado — Tensión político-técnica
El cliente quiere conversión 100% automatizada: “un programa que yo pico sin que nadie lo toque, tiene que funcionar perfecto.” Esta expectativa choca con la realidad: los 25+ patrones de reimplementación para el batch de contabilidad requieren decisiones de diseño que el automatismo actual no puede tomar.

Lo que se puede automatizar: conversión de lógica de negocio, scaffolding, verificación de equivalencia funcional.
Lo que requiere experto: modelo de ejecución del batch, patrones de I/O, paralelismo.
Presentar como continuo, no binario
👀
El sesgo del optimismo
“En toda la cadena éramos todos optimistas hasta que llegamos al final.” Es patrón, no anecdota: el análisis parece manejable, los primeros módulos funcionan, y el penúltimo paso revela complejidad no anticipada.

Mitigación: Incorporar explícitamente 20–30% de esfuerzo adicional para “descubrimiento de complejidad oculta” en los stages finales de cada módulo, no en los primeros.
Planificar el 20–30% oculto
🌳
Ningún proveedor resuelve todo solo
Un banco gestionó simultáneamente: conversión determinística masiva, agentes de IA, herramientas de Holding, y el conocimiento de quien construyó el sistema original. “Un solo proveedor no me puede resolver todo — si se asociaban entre ellos, la propuesta no necesariamente es uno.”

El posicionamiento correcto: “somos el integrador que sabe qué herramienta usar en qué momento, y tenemos el conocimiento del sistema original que ningún otro tiene.”
Posicionamiento como integrador
💾
La infraestructura que se olvió
Un equipo que terminó la primera etapa de conversión se encontró bloqueado porque los ambientes para probar no estaban listos. “A alguien se le olvidaron los ambientes y la infraestructura.”

El plan de infraestructura (ambientes, pipelines CI/CD, herramientas de equivalencia, acceso a datos de prueba) se planifica en paralelo con el plan técnico — no como paso posterior.
Infraestructura = Day 0
💪
El builder del sistema tiene 40–60% menos RE
El proveedor que construyó el sistema original sabe qué hace cada módulo, qué reglas de negocio están embebidas, y dónde están los puntos de riesgo. Un competidor externo pasó 8 meses sin identificar la causa raíz del problema de performance en el bloque de contabilidad. El builder lo identifica en semanas.

Esta asimetría representa 40–60% de reducción en esfuerzo de Reverse Engineering vs. un competidor que no conoció el sistema.

⏱ Performance + Arquitectura

☐ Equivalencias IBM-utility catalogadas: SORT, JOINKEYS, COUNT, SKIP, NODUP, EDIT
☐ Infraestructura de parallel-run definida y lista
