What it is about

Document what a legacy system actually does — phase by phase, artifact by artifact — to enable its modernization with controlled risk. This is not a strategic agent: it is the one that does the work of reconstructing the system from the code.

Guiding principle. The code does not lie. First, everything the code knows is extracted through static analysis; people validate what is doubtful, they do not reconstruct what is obvious. Business logic is never inferred without evidence in the code: what cannot be determined is flagged [AMBIGUOUS] and taken to validation.

What the call graph recovers well

Blast radius (hubs) Cycles / SCCs Dead code Inquiry vs update (CQRS)

All derivable from the call structure: who calls whom, how often, what is never invoked.

What the call graph does NOT recover

Bounded contexts (domain) Copybook coupling Strangler Fig seams

The domain lives in the data graph (who touches what), not in the call graph. It requires additional signals and human validation.

The 5 phases in detail

Each phase produces artifacts in reproducible formats (tables, JSON, diagrams) with a verifiable completeness criterion.

0Setup & Inventory

Objective: a complete, verified catalog of all artifacts. Without a complete inventory, later analysis is incomplete by definition.

Does: collects sources (COBOL/RPG, JCL/WFL, copybooks, DASDL/DDL, CICS/BMS), counts LOC, identifies first-level dependencies, documents what is missing with its impact.

[ARTIFACT] Master Inventory   [BLOCKING] if the programs or the JCL/WFL are missing, work cannot start.

1Static Analysis

Objective: build the dependency graph and complexity metrics. It answers: what calls what, how often, and how complex it is.

Does: extracts the call graph (CALL/PERFORM/ENTER, RUN/INCLUDE in WFL), computes cyclomatic complexity per program, flags dynamic calls [AMBIGUOUS] and identifies dead code candidates.

[ARTIFACT] Call Graph   [ARTIFACT] Complexity Matrix

2Data Reverse Engineering

Objective: reconstruct the full data model: DMSII/VSAM structures, copybooks, relationships, and lineage (which program reads/writes what).

Does: translates DASDL/copybooks to a logical structure, consolidates the data dictionary, maps lineage per record, and flags COMP-3 fields and two-digit dates that need handling in the migration.

[ARTIFACT] Data Dictionary   [ARTIFACT] Data Lineage Map   [ARTIFACT] Logical ERD

3Business Logic Extraction

Objective: separate pure business logic from technical orchestration. Produce business-readable specifications.

Does: classifies each paragraph (business · orchestration · data access · presentation · infrastructure), extracts business rules with their line of evidence, and catalogs hardcoded values (amounts, factors, thresholds) for externalization.

[ARTIFACT] Functional Specifications   [ARTIFACT] Business Rules Catalog

Hardcoded values are business rules frozen in the code. Each fixed amount or percentage is documented as a rule and proposed for externalization to configuration in the target architecture.

4Domain Decomposition

Objective: group programs, data and rules into cohesive domains — the future bounded contexts — and propose the migration order.

Does: identifies candidate bounded contexts via multi-signal fusion (see the Signals tab), applies the Human-in-the-Loop gate, maps inter-domain dependencies and builds the wave plan.

[ARTIFACT] Domain Map   [ARTIFACT] Wave Plan   [ARTIFACT] HITL (Human in the Loop) adjudication queue

Domain signals

The business domain is not read from the call graph. It is recovered by combining several signals — almost all extractable from the code through static analysis.

Bounded context = data ownership, not call structure. Two programs that never call each other belong to the same domain if they share the account or the accounting-entry layout. That is why copybook coupling is the strongest signal, and why it is invisible in the call graph.

Human-in-the-Loop pattern

The final bounded-context cut is a high regulatory-risk human decision: a badly placed seam equals a failed Strangler Fig. The domain is not auto-decided.

The AI proposes, the human disposes. Neither does the human review all 830 programs (it does not scale), nor does the AI decide on its own (forbidden). The AI does the heavy lifting and spends the scarce SME time only where there is doubt or risk. It arrives with evidence, a proposal and the confidence figure — never with open questions.

Confidence gate — defines what escalates to the human

HIGH CONFIDENCE  ·  the signals agree
Auto-accepted. The human does a sampled spot-check.
MEDIUM CONFIDENCE  ·  one signal corroborates, the rest abstain
The human reviews the proposal the AI already formed.
LOW CONFIDENCE  ·  active conflict among signals
Leakage node, shares a cross-domain copybook, or hangs off a hub. [ADJUDICATE→SME] — the human decides, mandatory.

Three mandatory Phase 4 gates

  • Gate 1 — after extraction. The human validates the naming-convention map and the copybook → domain glossary. Cheap and highest leverage: it corrects hundreds of assignments at once.
  • Gate 2 — on conflicts. Only the LOW CONFIDENCE ones go up for adjudication. Tens, not hundreds.
  • Gate 3 — seam confirmation. The final bounded-context boundaries are signed by the business SME and the architect before the wave plan. Regulatory gate.
[INVARIANT]. Every human decision is recorded in the adjudication queue and fed back: what is already resolved is not asked again.

Interviews with business SMEs

When static analysis produces [AMBIGUOUS] items, they are completed with structured interviews. The interview validates and resolves doubts: it does not reconstruct from scratch.

Order matters. Interviewing before static analysis is expensive and unreliable: whoever wrote the COBOL is gone, and whoever remains remembers poorly. First, everything the code knows is extracted, the interview is reached with a concrete map, and the SME time is used to validate what is doubtful — not to reconstruct what is obvious.

The bounded role of the interview

  • Static analysis leaves candidate seams with doubtful zones (leakage nodes, those hanging off shared hubs).
  • The SME confirms or corrects what the code already suggested; they do not discover the domain from scratch.
  • Resolves the [AMBIGUOUS] items that analysis cannot determine alone (intent of a hardcoded value, conditional path, apparent dead code).
  • Signs the final seams together with the architect (Gate 3).

Question guide by type of ambiguity

Hardcoded values
"In CREDVAL the maximum limit is fixed at $500,000. Does this value change often? Should it be configurable per product or per customer segment?"
Complex conditional logic
"This program has 3 distinct paths for mortgage loans. When is each one taken and what business decision drives it?"
Dead code candidate
"OLDPROC does not appear called from any program. Is it run in some way not in the code — an external scheduler, manual execution?"
Undocumented business rule
"The program computes the limit by multiplying the average balance by 5. Where does that factor come from? Is it in some policy or regulation?"
Ambiguous seam (LOW CONFIDENCE)
"LONB0444 is named as 'loans' but mostly calls 'deposits' programs and shares the accounting entry with GL. Which business capability does it really belong to? Where should the service boundary sit?"
Outcome. Each answer resolves an [AMBIGUOUS] item or confirms a seam, is recorded in the adjudication queue, and stops being a question. The system ends up documented by what the code proves plus what the business confirms.
