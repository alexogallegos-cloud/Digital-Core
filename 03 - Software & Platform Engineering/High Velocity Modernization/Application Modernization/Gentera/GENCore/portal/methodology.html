El conocimiento que nadie escribió

Por qué el código legacy oculta sus propias reglas de negocio.

01
Nadie documentó la lógica cuando la escribió
El desarrollador original que conocía el contexto de negocio ya no está. El código fue escrito con urgencia, sin comentarios ni especificaciones. El documento Word que acompañaba al proyecto se perdió en una carpeta compartida de 2014.
Consecuencia: entrevistas que generan versiones contradictorias
02
Las reglas viven en la estructura del código, no en comentarios
Un IF iv_campo IS INITIAL no dice "campo obligatorio": dice exactamente eso, pero en el idioma de la máquina. Para leerlo como regla de negocio hace falta traducir, clasificar y contextualizar.
Consecuencia: migración sin lista de reglas verificable
03
La lectura manual no escala a miles de objetos
Un analista experto puede revisar 5 programas ABAP por día con cuidado suficiente para extraer reglas fiables. Un landscape bancario típico tiene entre 3,000 y 20,000 objetos Z. A ese ritmo, el inventario tardaría años en completarse y estaría desactualizado antes de terminar.
Consecuencia: decisiones de modernización sin base de conocimiento
El principio que lo hace posible

El código ABAP es una especificación de negocio ejecutable. Cada sentencia que controla el flujo describe una regla que el negocio impuso al sistema.

Principio 1

Toda guarda de validación es una regla de negocio

Cada IS INITIAL o NE 0 en el código no es código defensivo: es la transcripción de una regla que alguien decidió en una reunión de negocio hace años. Podemos recuperarla.

Principio 2

Los mensajes de error revelan obligaciones regulatorias

Un MESSAGE E no es un mensaje genérico: el namespace del mensaje apunta directamente al marco regulatorio que lo originó. CNBV, Banxico, CONDUSEF, IFRS, todos dejan su firma en el código.

Principio 3

Los patrones son reproducibles y automatizables

Los mismos 6 patrones de detección que identificamos en un archivo funcionan en todos los objetos del landscape. La extracción es sistemática y escala a miles de programas sin esfuerzo humano adicional por objeto.

Principio 4

El resultado es consultable por agentes de IA

El Digital Brain no es un reporte PDF que se lee una vez. Es una base de conocimiento SQLite con índices vectoriales que cualquier agente puede consultar en lenguaje natural: "¿qué reglas afectan al cálculo de crédito grupal?"

Los 6 patrones de detección

Cada patrón ABAP es la firma de una regla de negocio específica.

Patrón 1 · Guarda de parámetro
Parámetro obligatorio
IF iv_campo IS INITIAL.
Regla: El nombre del parámetro es campo obligatorio para continuar la operación.
VALIDACION
Patrón 2 · Control de retorno SQL
Entidad no encontrada
IF sy-subrc NE 0.
Regla: Si la entidad no existe en base de datos, la operación no puede continuar.
VALIDACION
Patrón 3 · Mensaje de negocio
Señal regulatoria IFRS
MESSAGE eNNN(/z_namespace/msg_clase) TYPE 'E'.
Regla: La condición viola una obligación normativa. El namespace del mensaje revela el marco regulatorio aplicable.
MANEJO_ERROR
Patrón 4 · Excepción de sistema
Manejo de error técnico
CATCH cx_sy_itab_line_not_found zcx_entidad_no_encontrada.
Regla: Si el sistema falla al buscar la entidad, el proceso debe capturar el error y manejarlo.
MANEJO_ERROR
Patrón 5 · Filtro paramétrico
Control de flujo por datos
SELECT SINGLE * INTO ls_config FROM ztabla_cfg WHERE name EQ iv_campo.
Regla: El comportamiento del proceso depende del valor del parámetro en tabla de configuración.
FLUJO
Patrón 6 · Singleton + persistencia
Instancia única de control
IF NOT og_instance IS BOUND. CREATE OBJECT og_instance. UPDATE ztabla_config SET valor = iv_valor.
Regla: Solo puede existir una instancia del gestor de parámetros. El valor calculado se persiste en base de datos.
FLUJO · CALCULO

Implicación para la modernización

Cualquier equivalente TO-BE debe replicar el mismo comportamiento con la misma semántica normativa. El test de equivalencia no puede reducirse a "mismo output": debe verificar que el contexto regulatorio se preserve en el sistema destino.

El motor inspecciona el namespace de cada mensaje de error y lo cruza con el catálogo de marcos normativos. Sin entrevistas, sin supuestos manuales.
Taxonomía del Digital Brain

Cada regla extraída se clasifica en tres dimensiones independientes.

Tipo de regla

FLUJO
control de proceso
VALIDACION
integridad del dato
MANEJO_ERROR
tratamiento de excepción
CALCULO
persistencia de valor
Los tipos son mutuamente excluyentes por regla. Una regla puede reflejar múltiples tipos solo cuando el patrón ABAP combina control de flujo con persistencia de datos.

Nivel de riesgo

BAJO
operación estándar
MEDIO
impacto normativo
El riesgo MEDIO se asigna cuando la regla está asociada a un mensaje regulatorio, maneja tipos monetarios sin redondeo explícito, o controla acceso a datos sensibles. Es el primer filtro para priorizar tests de equivalencia funcional.

Señales regulatorias

Marco normativo
marcadas para revisión
Sin señal
sin marco normativo
La señal regulatoria se detecta automáticamente por el namespace del mensaje de error (patrón 3). Al crecer el corpus se esperan señales adicionales: CNBV (BSDK), CONDUSEF y normas de cartera vencida Banxico.

El camino desde aquí

Escalar el Brain
al landscape
completo de Gentera.

Paso 1 — Carga de corpus
Recibir los archivos .abap del landscape Gentera y organizarlos en source/. El pipeline corre sin cambios de configuración sobre cualquier volumen de código. Con 50 objetos el Brain tendrá una visión representativa.
Paso 2 — Validación con negocio
Revisar las reglas extraídas con el equipo de negocio de Gentera. El Brain genera una página HTML por objeto con todas sus reglas; la sesión de validación tarda horas, no semanas, porque el punto de partida ya está estructurado.
Paso 3 — Catálogo de equivalencia
Las reglas validadas se convierten en la especificación de los tests de equivalencia funcional del proyecto de modernización. Cada regla del Brain es un caso de prueba. El shift-left de QE ocurre de forma natural.
Para arrancar necesitamos
  • Archivos .abap — exportados de SE38, SE24 o descarga de repositorio
  • Contacto de negocio — quién valida la semántica de las reglas extraídas
  • Versión SAP — ECC 6.0 o S/4HANA para confirmar la compatibilidad del extractor y el alcance del análisis
