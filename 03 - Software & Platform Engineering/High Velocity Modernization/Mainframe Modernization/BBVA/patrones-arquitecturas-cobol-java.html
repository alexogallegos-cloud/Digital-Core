Modernización de Batch COBOL a Java
Patrones, anti-patrones y arquitecturas

Guía técnica framework-agnóstica (Java · Spring Boot · Quarkus · Jakarta Batch) para migrar procesos batch de alto volumen sin heredar la degradación de desempeño típica de una traducción literal.

Principio rector: el reto no está en el lenguaje, está en el modelo de ejecución. Se re-ingeniería el proceso —streaming, chunk, bulk, partición, decimal exacto— no se transpila línea por línea.
01

Patrones correctos

Las decisiones de diseño que permiten a Java igualar o superar la ventana de proceso del mainframe. Están agrupadas por el tipo de problema que resuelven: cómo se mueven los datos, cómo se estructura el proceso, cómo se garantiza la exactitud y cómo se despliega.

Grupo ACómo se mueven los datos (entrada / salida)La causa #1 de degradación vive aquí
1

Lectura en streaming

En lugar de traer toda la tabla a memoria, el proceso lee los registros de a poco: un cursor server-side los va entregando en flujo, con un fetch size alto que imita el blocking factor con el que el mainframe leía sus archivos. Así nunca se cargan millones de filas de golpe.

Framework recomendadoSpring Batch · JdbcCursorItemReader — alt: MyBatis Cursor · jOOQ streaming
2

Datos de referencia en memoria

Los catálogos y tablas paramétricas se cargan una sola vez al arrancar el step y quedan en un mapa en memoria. Cada registro los consulta ahí mismo, no en la base de datos — que es justo lo que evita el efecto N+1 (una consulta por registro).

Framework recomendadoCaffeine (cache en memoria) — alt: Ehcache · HashMap en @BeforeStep
3

Escritura masiva (bulk)

Las escrituras no van una por una: se acumulan y se mandan en lote (executeBatch, o COPY en Postgres). El tamaño del lote se alinea al commit del chunk, para que la escritura y la transacción avancen al mismo ritmo.

Framework recomendadoSpring Batch · JdbcBatchItemWriter — alt: PostgreSQL COPY · jOOQ batch
4

Procesamiento set-based

Lo que la base de datos hace mejor —filtrar, cruzar (join) y agregar— se le delega escribiéndolo en SQL (push-down). Java coordina el proceso; el motor resuelve el conjunto completo de una sola pasada, en vez de traer todo a Java para recorrerlo.

Framework recomendadojOOQ o MyBatis (SQL push-down) — alt: SQL nativo + JDBC
Grupo BCómo se estructura el proceso batchEl ritmo de trabajo que replica al mainframe
5

Procesamiento chunk-oriented

El trabajo se procesa en lotes (chunks) de N registros: se leen, se procesan y se escriben juntos, y recién ahí se hace un commit. Es el equivalente moderno del loop de COBOL con checkpoint — no un commit por cada registro.

Framework recomendadoSpring Batch (chunk-oriented step) — alt: Jakarta Batch / JBeret
6

Checkpoint / restart

El proceso va guardando hasta dónde llegó (qué chunk terminó). Si algo falla, retoma desde ese punto y no desde el principio —igual que el CHKPT del mainframe—, de modo que un incidente no obliga a repetir toda la ventana batch.

Framework recomendadoSpring Batch · JobRepository — alt: Jakarta Batch
7

Particionamiento

Para ir más rápido, el trabajo se divide en particiones independientes (por rango de cuenta, por sucursal) que corren en paralelo. Dentro de cada partición el orden se conserva —que es lo que la contabilidad exige—; la unidad que se reparte es la partición, nunca el registro suelto.

Framework recomendadoSpring Batch Partitioning — distribución entre nodos con Apache Kafka o RabbitMQ (remote partitioning)
Grupo CCorrectitud financieraDonde un error no es lento, es incorrecto
8

Aritmética decimal exacta

Todo importe se maneja con BigDecimal, con la misma escala y el mismo modo de redondeo que usaba el COBOL. Nunca con double: la coma flotante binaria arrastra errores de centavos que rompen la equivalencia contable.

Estándar JDKjava.math.BigDecimal — sin dependencia externa; fijar escala y RoundingMode
9

Capa de ingesta que decodifica

Antes de procesar nada, una capa de entrada convierte los formatos del mainframe (COMP-3, EBCDIC, binario) a tipos nativos de Java, una sola vez y guiada por los copybooks. Si se salta este paso, los valores salen mal desde el primer registro.

Framework recomendadoJRecord o Cobrix (copybooks COMP-3) — Apache Camel (Bindy/BeanIO) para orquestar la ingesta
Grupo DArquitectura y disciplinaDónde y cómo corre el proceso
10

Tier de batch separado

El batch de alto volumen corre en su propio entorno, aislado de los servicios online (request/response) y pegado a su base de datos. Meter el batch dentro del plano online es una de las causas típicas de la degradación.

Despliegue / orquestaciónArgo Workflows · AWS Batch · Kubernetes Jobs — alt: Control-M (scheduling heredado del JCL)
11

Co-localización cómputo-datos

El cómputo se coloca cerca de los datos (misma zona/VPC, réplica local) para que cada acceso no se convierta en un viaje de red. Esa cercanía entre proceso y datos era gratis en el mainframe; en la nube hay que reconstruirla a propósito.

InfraestructuraMisma VPC/AZ + réplica de lectura — p.ej. Amazon Aurora — decisión de despliegue, no framework
12

IA acelera, humano valida

Las herramientas de IA aceleran la traducción del código, pero la lógica financiera y regulatoria siempre la revisa una persona. La IA propone; el experto valida y firma.

Tooling IAAmazon Q Developer Transform · IBM watsonx Code Assistant for Z — alt: GitHub Copilot · + revisión humana
02

Anti-patrones

Las decisiones que producen código funcionalmente correcto pero con desempeño degradado (relaciones 1:10 o peores).

1

Traducción literal registro por registro

Preservar la lógica procedimental del COBOL en Java sin re-ingeniar el modelo de ejecución.

Consecuencia: se hereda el peor patrón de desempeño posible.
2

N+1 · una consulta por registro

Reemplazar la lectura secuencial de un archivo por una consulta a BD por cada registro.

Consecuencia: degradación de 10× a 100×. Causa #1.
3

Batch como microservicios chatty

Descomponer un batch monolítico en servicios que se llaman por REST en el hot path.

Consecuencia: cada iteración interna se vuelve una llamada de red. Catastrófico.
4

Distribución por registro

Paralelizar con granularidad fina (un mensaje/llamada por registro) en lugar de por partición.

Consecuencia: overhead de red y serialización domina el tiempo.
5

Escritura fila por fila

INSERT/UPDATE individuales en lugar de operaciones en lote.

Consecuencia: millones de round-trips a la base de datos.
6

ORM en el hot path del batch

Usar Hibernate/JPA para el camino de datos masivo, con lazy loading y dirty-checking.

Consecuencia: N+1 encubierto, consumo de memoria de sesión, lentitud.
7

Commit por registro

Una transacción por cada registro procesado.

Consecuencia: el overhead de commit domina el tiempo total.
8

double para importes

Usar coma flotante binaria "por desempeño" en cálculos financieros.

Consecuencia: errores de redondeo = descuadre contable auditable.
9

Cargar todo en memoria

Traer millones de filas a un List antes de procesar.

Consecuencia: presión de memoria, GC, OutOfMemory en volumen real.
10

Multi-threading donde importa el orden

Paralelizar un step cuyo resultado depende del orden de aplicación.

Consecuencia: saldos intermedios incorrectos aunque cada operación sea válida.
11

Batch dentro del tier online

Ejecutar proceso masivo dentro de la plataforma de servicios request/response.

Consecuencia: contención de recursos y modelo de ejecución equivocado.
12

Reglas inferidas de conocimiento genérico

Dejar que la herramienta "rellene" una fórmula estándar de mercado en vez de replicar la regla real del código.

Consecuencia: resultado plausible pero incorrecto.

Errores típicos de traducción

Construcciones específicas de COBOL/JCL que no tienen equivalente directo en Java y que, mal resueltas, producen resultados lentos o incorrectos.

COMP-3 / packed decimalSe trata como texto plano → valores incorrectos desde el primer registro.Decodificar en la capa de ingesta con base en el copybook antes de procesar.
REDEFINESMisma posición de memoria, distintos tipos; se generan clases separadas que rompen la semántica compartida.Patrón union / tagged-type o BitBuffer; probar cada layout del overlay.
JOINKEYS (SORT)El match entre archivos pierde o duplica registros; nested-loop O(n²) donde había merge-join O(n).Merge-join sobre flujos pre-ordenados o join en la BD; replicar el sort key.
Ordenamientos implícitosLas utilerías ordenan antes del match; si no se replica, el resultado diverge.Documentar y replicar el criterio de orden exacto de cada utilería.
COUNT · SKIP · NODUP · EDITInstrucciones propietarias de las utilerías IBM que el agente no conoce nativamente.Catálogo de equivalencias utilería→Java por instrucción, probado.
STRING / UNSTRINGConcatenación/división con delimitadores y manejo de overflow que Java no replica con operaciones estándar.Helpers Java verificados en casos borde.

Arquitecturas propuestas

Los cuatro diagramas de referencia que materializan los patrones y evitan los anti-patrones.

A · Separación de tiers: online vs. batch

Los microservicios distribuidos son el patrón correcto para el plano online (baja latencia, request/response). El batch de alto volumen quiere cohesión y localidad de datos. Son problemas de diseño distintos y se despliegan por separado.

Tier online Quarkus / Spring Boot
Servicios REST · baja latencia · request/response · consultas y operaciones transaccionales de canal.
↕  comparten datos, no el request path
Tier batch (dedicado) Spring Batch / Jakarta Batch
Proceso masivo cohesivo · chunk-oriented · particionado · co-localizado con su BD · orquestado por scheduler.
↓
Datos
Base de datos con índices correctos · bulk load · réplica local para el tier batch.

B · Anatomía del batch chunk-oriented

El lote de N registros se lee en streaming, se procesa con lookups en memoria y se escribe en bloque; un solo commit por lote. El ciclo se repite hasta agotar la entrada, con restart desde el último chunk confirmado.

Reader
cursor streaming · fetch size alto · ordenado
›
Processor
lookup en memoria · BigDecimal exacto
›
Writer
escritura masiva · executeBatch
›
Commit
1 por chunk (N=1k–10k)
↻ se repite por cada chunk · JobRepository persiste el punto de reinicio

C · Escalamiento por particionamiento

Para volumen que no cabe en un nodo, se divide el trabajo en particiones independientes (por rango de cuenta o sucursal). Cada worker procesa su partición end-to-end localmente. La unidad de distribución es la partición —miles de registros— nunca el registro individual.

Clave: distribución coarse-grained (por partición) = paralelismo real sin el overhead de red del anti-patrón chatty y sin romper el orden contable dentro de cada partición.

D · Estrategia de migración por dominio

No todo dominio debe dar el salto directo a cloud-native al mismo tiempo. Para el núcleo batch de mayor criticidad, un puente de replatform reduce el riesgo antes del refactor. La decisión se toma por workload.

Paso 1 · Puente
Replatform
Recompilar/rehospedar preservando el modelo de I/O y batch. Sale del mainframe con riesgo bajo y desempeño cercano.
→
Paso 2 · Objetivo
Refactor cloud-native
Reimplementación Java dominio por dominio con los patrones de este documento y equivalencia ≥ 99.99%.
Regla de decisión: batch de alto volumen y secuencial → replatform primero, refactor después. Online de baja latencia → refactor directo a microservicios. Lógica crítica → equivalencia + parallel-run, sin importar la ruta.
