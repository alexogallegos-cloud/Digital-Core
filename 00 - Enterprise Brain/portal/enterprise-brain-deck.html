La diferencia que hace el conocimiento

El mismo proyecto. Dos puntos de partida distintos.

Sin Enterprise Brain

El sistema es una caja negra

  • Las decisiones de diseño se basan en entrevistas y documentación parcial
  • Los defectos de equivalencia funcional se descubren en producción
  • Cada nuevo integrante del equipo reinicia el aprendizaje desde cero
  • La complejidad real aparece durante la ejecución, cuando el costo de cambio es máximo
  • La regulación aplicable a cada módulo se asume, no se verifica
Con Enterprise Brain

El sistema legacy es legible antes del primer commit

  • Las reglas de negocio son cuantificables: N reglas, M dominios, K lógicas regulatorias con trazabilidad
  • Los gaps de capability se identifican antes del diseño target, no después del go-live
  • El vocabulario empresarial es compartido entre el equipo Accenture y el cliente desde el día uno
  • La equivalencia funcional se verifica con evidencia del brain, no con intuición del desarrollador
  • Cualquier nuevo integrante tiene acceso instantáneo al contexto completo del sistema
El Enterprise Brain

Cuatro capas de conocimiento,
un solo brain consultable.

Capa 1 — Lenguaje

El vocabulario empresarial del cliente

Términos, definiciones y relaciones entre conceptos del negocio extraídos del código fuente. Base común para todo el equipo y hilo conductor de los demás capas.

Capa 2 — Almas

Los módulos funcionales del sistema

Grupos de lógica cohesiva identificados por patrones de llamada, dominio de datos y puntos de entrada. Cada alma tiene nombre de negocio y propósito claro.

Capa 3 — Biografía

Los flujos end-to-end del negocio

Customer journeys trazados desde el código fuente, no desde el PowerPoint. Cada flujo muestra qué lógica activa, en qué dominio y con qué dependencias externas.

Capa 4 — Intención

Las reglas de negocio del sistema

Cada fórmula, validación, umbral y transformación identificada, clasificada (NEGOCIO, INFRAESTRUCTURA, ENSAMBLAJE, PRESENTACION) y nombrada en lenguaje empresarial mediante síntesis con Claude.

Pipeline de construcción
Bronze → Silver → Gold
Bronze
extract-rules.py lee el código fuente y produce JSON crudo por componente — sin interpretación semántica, solo extracción estructural del código.
Silver
enrich-rules.py clasifica cada regla (clase, regulación) y sintetiza el business_name con Claude leyendo el SP completo en context — no el fragmento aislado.
Gold
build-brain.py carga en SQLite con FTS5, mapeo ETB L3 y federación ATTACH lista. Idempotente: marks de alta confianza no se sobreescriben.

Arquitectura del conocimiento

Cuatro capas independientes, un brain coherente.

Capa 1
Lenguaje
Fuentes y output
Fuentes — nombres de SPs, tablas, campos, comentarios, documentación interna
Output — tabla vocabulary con términos confirmados, definición y scope
Gate — mínimo 50 términos confirmed antes de salir de DISCOVER
Regla V1 — vocabulario del cliente es cross-sistema, no por brain
Capa 2
Almas
Identificación
fan_in / fan_out — los SPs más llamados y los que más llaman son candidatos a alma
Co-call clustering — SPs que siempre se llaman juntos forman un alma
CTM entry points — cada job batch ancla un alma de proceso
Bautismo — nombre de negocio obligatorio, nunca técnico
Capa 3
Biografía
Tipos de entry points
CTM_ENTRY — jobs batch de Control-M o equivalente scheduler
ESB_EXPOSED — servicios expuestos por ESB / API gateway
CHANNEL — puntos de entrada desde canales digitales
SCHEDULED — procesos con trigger temporal propio
Capa 4
Intención
Clases de regla

Modelo de entidades
Nueve tablas,
un modelo de conocimiento coherente.
Cada brain.db implementa el mismo schema canónico — independientemente de la tecnología del sistema fuente. El schema es el contrato.
system_info — identidad y estado del sistema
└── components N componentes (SPs, APIs, jobs)
├── rules clase · reg · riesgo · business_name
├── journeys entry_type · call_depth
├── souls módulos funcionales por clustering
└── etb_l3 261 capabilities L3 embebidas
vocabulary cross-sistema · scope · maturity
cross_dependencies └── external_systems

El primer paso

El brain existe
cuando existe
el acceso al código.

Paso 1 — Diagnóstico
Compartir acceso al repositorio del sistema legacy. En dos semanas el Specialist RE produce el inventario de componentes y la estimación de olas de extracción. Sin compromiso de modernización aún.
Paso 2 — Brain Bootstrap
Brain.db inicializado con schema canónico, vocabulario Capa 1 y almas Capa 2. El equipo puede consultar el sistema antes de que termine la extracción completa. Valor visible desde la semana tres.
Paso 3 — Activación
Con DoD-EB-01 a DoD-EB-10 cumplidos, el brain gobierna el diseño de los microservicios target. Los Digital Twins interrogan el brain antes de cada decisión de arquitectura. La modernización empieza con conocimiento, no con supuestos.
Para arrancar necesitamos
  • Código fuente — Repositorio o dump del sistema (SPL, COBOL, ABAP, PL/SQL, T-SQL, Java EE)
  • Contacto técnico — DBA o arquitecto del sistema para resolver dudas semánticas puntuales
  • Nomenclatura — Documentación de dominios y procesos del cliente (aunque sea parcial)
  • Dos semanas — Ventana inicial para el Bootstrap del brain con la primera ola de extracción
